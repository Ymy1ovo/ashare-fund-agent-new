## 1. 两个佣金计算模型的区别与最终选择

### 1.1 per_fill（按笔）

```text
每笔成交佣金 = max(该笔成交金额 × 费率, 最低佣金)
```

同一订单分 N 次成交就收 N 次最低佣金。

### 1.2 per_order（按订单累计，本项目默认）

```text
订单累计应收佣金 = max(订单累计成交金额 × 费率, 最低佣金)
本次新增佣金     = 订单累计应收佣金 − 该订单已收佣金
```

同一订单的多次分笔成交**共用一份最低佣金额度**。

### 1.3 最终采用

**`per_order` 为默认**，配置项 `CostConfig.min_commission_model` 可切换。

| 理由 | 说明 |
| --- | --- |
| 贴近结算实际 | 一次委托的分笔成交通常按一笔结算 |
| 避免成本失真 | per_fill 会让多日小额成交重复收 5 元，人为放大成本 |
| 可对比 | per_fill 保留为选项，便于做成本敏感性分析 |

**明确声明**：这是本项目的模拟假设，不代表所有券商的实际结算方式。
实际券商可能按分笔成交逐笔计费，报告与代码注释均已标注。

## 2. 同一订单多次部分成交的费用计算示例

### 2.1 卖出 737 股，分两日成交（500 + 237）

价格约 10.0 元，费率 0.025%，最低佣金 5 元。

| 成交 | 数量 | 成交金额 | 累计金额 | 累计应收 | 已收 | **本次增量** |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 700 | 6,996.50 | 6,996.50 | max(1.75, 5) = 5.00 | 0 | **5.00** |
| 2 | 37 | 369.81 | 7,366.31 | max(1.84, 5) = 5.00 | 5.00 | **0.00** |
| 合计 | 737 | 7,366.31 | — | 5.00 | — | **5.00** |

对比 `per_fill`：`5.00 + 5.00 = 10.00`，多收一倍。

### 2.2 超过最低佣金门槛后的情况

| 成交 | 数量 | 金额 | 累计金额 | 累计应收 | 已收 | 本次增量 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4,000 | 40,000 | 40,000 | 10.00 | 0 | **10.00** |
| 2 | 4,000 | 40,000 | 80,000 | 20.00 | 10.00 | **10.00** |
| 合计 | 8,000 | 80,000 | — | 20.00 | — | **20.00** |

首笔已超门槛，之后只按费率累加，不再触及最低佣金。

### 2.3 多项费用分离

```python
fee = incremental_commission(...)       # 佣金（含最低佣金规则）
stamp, transfer = taxes(gross, config)  # 印花税、过户费，按金额独立计算
fee += stamp + transfer
slip = slippage_cost(...)               # 滑点，单独记录
```

实测：成交 1,000 元、费率 0.025%、最低 5 元、印花税 0.1%、过户费 0.001% → 5.00 + 1.00 + 0.01 = 6.01 元。
最低佣金只作用于佣金本身，不吞并税费。

## 3. 零碎股交易规则及测试

### 3.1 规则

| 意图 | 判定 | 申报数量 |
| --- | --- | --- |
| 全部清仓 | `Order.liquidate == True`（引擎侧 `target_weight <= 1e-9`） | 全部可卖数量，整手+零股一笔 |
| 部分减仓 | `liquidate == False` | 整手向下取整 |
| 部分减仓但只剩零股 | `liquidate == False` 且可卖 < 一手 | 整笔卖掉该零股 |

**不能只看「是否超过 100 份」决定是否允许零股。**

### 3.2 实测七场景

| 场景 | 委托 | 成交 | 剩余 |
| --- | ---: | ---: | ---: |
| 持仓 130,400，清仓 | 130,400 | 130,400 | **0** |
| 持仓 537，清仓 | 537 | 537 | **0** |
| 持仓 1,237，清仓 | 1,237 | 1,237 | **0** |
| 持仓 1,237，卖 500 | 500 | 500 | 737 |
| 持仓 537，卖 500 | 500 | 500 | 37 |
| 持仓 99，清仓 | 99 | 99 | **0** |
| 持仓 100，清仓 | 100 | 100 | **0** |

### 3.3 浮点误差

策略输出 `130,399.7`、`130,400.0001`、`130,399.9999` 时，清仓分支一律返回 `130,400`（全部可卖），
不会生成 1 份或 2 份的残余订单。

### 3.4 T+N 约束保持

清仓仍先取 `portfolio.available(code, trade_date)`。
买入 500 股（300 股 T+1 可卖 + 200 股 T+2 可卖）下，第一天只能卖 300，第二天卖剩余 200。

## 4. 全池压力测试统计口径

### 4.1 上一阶段数字不一致的原因

| 数字 | 出处 | 参数 |

**根因是参数不同，不是口径冲突。** 但报告并列两个数字未说明参数差异，属表述缺陷。

### 4.2 统一口径

新增 `metrics.return_sample_stats()`，全项目唯一入口，输出可加总五元：

```text
nav_days = first_day + held_price_gap + prior_day_price_gap + missing_nav + valid_return_days
```

| 字段 | 定义 |
| --- | --- |
| `nav_days` | 每日快照总数 |
| `first_day` | 首日无前值，不产生日收益 |
| `held_price_gap` | 持仓 ETF 缺有效报价 |
| `prior_day_price_gap` | 前日估值不完整，本日收益不可信 |
| `missing_nav` | 净值缺失或前值为 0 |
| `valid_return_days` | 可用日收益数量 |

`evaluate_sparse_result()` 强制校验加总，不成立直接判 `failed`。

### 4.3 本轮验证口径

代表性池与全池**使用同一 MA 窗口（MA60）与同一统计函数**，数字可直接对比：

| 池 | 快照 | 首日 | 缺口 | 缺净值 | 有效 | 加总 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 代表性池（6 只） | 447 | 1 | 176 | 0 | **270** | `1+176+0+270=447` ✓ |
| 全池（41 只） | 447 | 1 | 177 | 0 | **269** | `1+177+0+269=447` ✓ |

不再有互相矛盾的数字。

## 12. 策略结论（未变）

**工程整改通过不代表策略有效。**

上一轮全池验证（`32aead3291734f91`）：

| 项目 | 样本内 | 样本外 |
| --- | ---: | ---: |
| 总收益 | -16.33% | 32.21% |
| Sharpe | 0.1058 | 0.7859 |

对照全池样本外基准：

| 基准 | 总收益 | Sharpe | 最大回撤 |
| --- | ---: | ---: | ---: |
| **等权买入持有** | **31.97%** | **0.8805** | **-18.58%** |
| MA250 趋势 | 32.21% | 0.7859 | 更大 |

趋势策略收益略高，但 **Sharpe 更低、回撤更大、交易次数多一个数量级**。
样本内普遍为负、样本内外反向、参数对池高度敏感——**不能宣布策略验证通过**。

历史回测收益不构成未来收益承诺。
