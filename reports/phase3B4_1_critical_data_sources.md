### 1.2 公告接口的关键性质

```
http://api.fund.eastmoney.com/f10/JJGG/?callback=jQuery&fundcode={code}
&pageIndex=1&pageSize=100&type=0
```

| 性质 | 实测结果 |
| --- | --- |
| 是否公开 | ✅ 无需认证 |
| 是否覆盖已终止基金 | ✅ **能查到 150019/184688 等已注销代码的全部历史公告** |
| 单只公告数 | 100 ~ 1,100 条 |
| 关键字段 | `TITLE`、`PUBLISHDATEDesc`、`ID`、`FUNDCODE` |
| 证据等级 | **B 级**（第三方结构化列表，可追溯到原文） |

### 1.3 公告原文的两个形态

```
http://pdf.dfcfw.com/pdf/H2_{公告ID}_1.pdf
```

| 公告年代 | 实测返回 | 处理方式 |
| --- | --- | --- |
| 约 2015 年后 | 真正的 PDF 文件 | `pypdf` 提取正文 |
| 约 2015 年前 | **HTML 正文**（不是 PDF） | 剥标签取文本 |

**这是本轮踩到的一个坑**：第一版只判断 `%PDF` 魔数，把 2014 年前的老公告
全部判成「不可读」，导致 `pdf_readable` 只有 17/25。
改成兼容 HTML 后变成 **24/25**。

**教训**：数据源的实际返回格式可能随年代变化，不能只测新样本就下结论。

### 2.6 四类事件必须分开

本轮**踩过两个分类错误**，都已修正并用测试锁住：

| 错误 | 后果 | 修正 |
| --- | --- | --- |
| 「终止分级运作变更而来」被判为 `liquidation` | 把**份额终止**误报成**基金清盘** | 规则前置 `终止分级运作` → `share_termination` |
| 「终止上市及转型期间…变更」被判为 `delisting` | 把**转型**误报成**终止上市** | 规则前置 `终止上市及转型` → `transformation` |

这两类错误如果混进名录，会让「历史上有多少基金清盘」这个统计完全失真。

### 2.7 覆盖率能说多少

**能说的**：

- 25 只已终止基金中，25 只能查到公告，24 只能读到原文，24 只能提取终止日期。
- 证据等级 A 的有 24 只，全部来自基金公司正式公告原文。
- 公告接口对**已注销代码**依然返回数据，说明可以按事件反查。

**不能说的**：

- **无法给出「全市场清盘基金总数」的覆盖率**——因为没有一个权威的全量清单可以比对。
- 不能说「名录已经完整」。只能说「按代码域扫描 + 公告反查，能建立事件级名录」。

### 2.8 主要缺口

| 缺口 | 说明 |
| --- | --- |
| **没有权威全量清单** | 只能靠代码域扫描（1500xx/1846xx/1847xx 等）反推，容易漏 |
| 成立日期覆盖率低 | 只有 2/25 只提取到 `established_date`，公告里通常不写 |
| 承接基金代码缺失 | 18 只提取到承接基金**名称**，但代码一个都没有——公告里常不写 |
| 净值数据不完整 | `150001` 的净值接口返回 404（东财已删除） |
| 非分级类清盘基金样本少 | 25 只里 18 只是「老封闭式/分级终止上市」，真正「清盘」只有 2 只 |

## 4. 费率证据等级说明

| 来源 | 等级 | 理由 |
| --- | --- | --- |
| 基金合同 / 招募说明书 PDF | **A** | 法律文件原文 |
| 基金公司费率调整公告 | **A** | 正式披露 |
| 天天基金 F10 费率页 | **C** | 页面自称「费率来源基金公司」，但属第三方展示 |
| 天天基金「优惠费率」 | **C** | 平台自己的折扣，**不等于支付宝** |
| 支付宝实际扣费 | **D** | 无公开数据源 |

### 4.1 必须区分的三个费率概念

| 概念 | 含义 | 能否获取 |
| --- | --- | --- |
| **合同费率** | 基金合同约定的最高费率 | 需从合同 PDF 提取（A 级） |
| **平台折扣费率** | 天天基金/支付宝自己的折扣 | 天天基金可抓（C 级），支付宝 unknown |
| **实际扣费** | 用户实际被扣的钱 | 只有账户流水能看到（D 级） |

**本轮只拿到「平台折扣费率」**，而且是**天天基金的，不是支付宝的**。
这一点必须在数据层里显式标注，不能当成支付宝费率使用。

## 5. 支付宝可购买状态可行性

### 5.1 结论

> **`not_obtainable` — 不能合法、稳定地自动获取。**

### 5.2 探测结果

| 站点 | 可达 | 状态码 | 有基金状态 API |
| --- | --- | ---: | --- |
| 支付宝主站 | ✅ | 200 | 无 |
| 支付宝开放平台 | ✅ | 200 | 无 |
| 蚂蚁集团官网 | ✅ | 200 | 无 |
| 支付宝基金子站 | ❌ | — | 无 |
| 支付宝基金产品页 | ❌ | — | 无 |

### 5.3 为什么不可获取

支付宝基金购买状态属于**登录态内的账户/渠道数据**，没有公开、稳定、合法的接口可以查询「某只基金在支付宝能否购买」。支付宝主站与开放平台均不提供面向第三方的基金可购买状态 API；基金子站需要登录且受访问控制。

### 5.4 必须区分的三个概念

| 概念 | 含义 | 数据源 |
| --- | --- | --- |
| `fund_open_subscription` | 基金合同层面开放申购，可用天天基金状态近似判断 | 天天基金状态近似 |
| `eastmoney_purchasable` | 天天基金作为销售渠道可购买，仅代表该渠道 | `fund_purchase_em` |
| `alipay_purchasable` | 支付宝作为销售渠道可购买，**无公开数据源** | **无** |

### 5.5 明确禁止的做法

- ❌ 尝试绕过登录/验证码/风控获取状态
- ❌ 使用非公开接口（逆向 APP 或网页私有 API）
- ❌ 把天天基金申购状态当作支付宝状态

### 5.6 推荐方案：保留 unknown + 人工核实

| 项 | 做法 |
| --- | --- |
| 存储 | fund_subscription_status.alipay_purchasable 保持 'unknown' |
| 人工流程 | 建立人工核实流程：在 fund_subscription_status 增记 verified_by='manual' + as_of_date + screenshot_path，由人工在支付宝 APP 内确认后录入 |
| 禁止推断 | 禁止由天天基金状态、基金合同开放申购状态推断支付宝状态 |

**已经在 3B-4.0 的 DDL 里落实**：
`fund_subscription_status.alipay_purchasable` 有 `CHECK (IN ('unknown','yes','no'))`
约束且默认 `unknown`，本轮验证了这个设计是正确的、也是必要的。

## 9. 尚未解决的问题

1. 清盘名录覆盖率无法量化：没有权威的全量清单可比对
2. 净值数据源只覆盖部分已终止基金（150001 返回 404）
3. 已终止基金的历史费率在公开渠道不可恢复
4. 支付宝可购买状态无公开合法接口
5. 合并承接基金代码仅部分公告明确写出

### 9.1 最严重的一条

> **无法给出「全市场清盘基金总数」，因此无法计算「清盘名录覆盖率」。**

这不是能力问题，是数据本身的问题：中国公募基金**没有一个公开的、
可批量下载的「已终止基金全量清单」**。基金业协会、证监会都不提供这种清单。

能做的只有两件事：

1. **代码域扫描**：按已知的代码段（150xxx 分级、184xxx 老封闭式）逐个探测公告接口；
2. **正向积累**：从现在起定期抓取全量存续清单，用**清单差异**反推新增的清盘。

第 2 条是唯一能长期逼近完整的方法，也是 3B-3 就提出的建议。

## 10. 最终结论

### 10.1 分项判定

| 问题 | 判定 | 依据 |
| --- | --- | --- |
| 历史清盘名录 | **有限继续** | 能按事件建立（A 级证据），但无法保证全量 |
| 赎回费阶梯 | **继续** | 存续基金可稳定解析（C 级），是回测必需 |
| 历史费率 | **停止** | 公开渠道不可恢复，只能人工 |
| 支付宝状态 | **停止** | 无公开合法接口，保持 unknown |

### 10.2 建议的下一步优先级

| 优先级 | 事项 | 证据等级 | 前置条件 |
| --- | --- | --- | --- |
| **P0** | 历史终止名录采集器（公告列表 + 原文解析） | A | 无，可立即做 |
| **P0** | 存续基金费率采集器（F10 页解析） | C | 无，可立即做 |
| P1 | 全量清单按日快照机制 | B | 需长期运行积累 |
| P2 | 承接基金代码人工补录 | A | 需人工 |
| P3 | 历史费率人工提取 | A | 需逐份合同 PDF |
| — | 支付宝状态 | — | **不做自动化** |

### 10.3 幸存者偏差立场（survivorship_bias 未完全解决）

**本轮没有解决幸存者偏差，只是把「完全没有」修正为「可以按事件建立」。**

| 项 | 状态 |
| --- | --- |
| 能否建立已终止基金名录 | ✅ 能（A 级公告原文） |
| 能否保证名录完整 | ❌ **不能** |
| 能否计算覆盖率 | ❌ **不能**（无权威全量清单） |
| 幸存者偏差是否消除 | ❌ **未消除** |

因此凡是基于「当前存续基金」做的历史回测，仍必须标注
`survivorship_bias_unresolved`。本轮只是为将来消除它提供了**可行的采集路径**。

### 10.4 一句话

> **「历史清盘名录完全没有」这个判断需要修正——它有，只是不成册。**
> 按事件反查能拿到 A 级证据；但「全量完整」和「历史费率」这两件事，
> 当前公开渠道确实做不到，只能标未解决。
