### 0.2 最重要的结论

> **数据源可用，但幸存者偏差无法消除，且交易规则大量缺失。**

| 层次 | 状态 |

**限制**：货币基金不支持（返回 `KeyError: 'data'`），必须走兜底。

### 2.4 关键验证发现

#### 发现 1：单位净值与累计净值必须分开，差额就是历史分红

| 代码 | 单位净值 | 累计净值 | 差额 | 分红次数 |
| --- | ---: | ---: | ---: | ---: |
| `000051` | 1.5402 | 1.5402 | 0.0 | 0 |
| `110020` | 1.6526 | 1.6526 | 0.0 | 0 |
| `161725` | 0.5791 | 2.2952 | 1.7161 | 3 |
| `012414` | 0.576 | 0.661 | 0.085 | 3 |
| `007300` | 3.0432 | 3.0432 | 0.0 | 0 |
| `007301` | 2.9802 | 2.9802 | 0.0 | 0 |
| `110022` | 3.01 | 3.01 | 0.0 | 0 |
| `161005` | 2.4727 | 5.5207 | 3.048 | 16 |
| `000478` | 2.8419 | 2.8419 | 0.0 | 0 |
| `000015` | 1.2109 | 1.6015 | 0.3906 | 9 |
| `000016` | 1.1968 | 1.5276 | 0.3308 | 9 |

**规律完全一致**：有分红的基金，累计净值 > 单位净值；差额随分红次数增加。
没有分红的基金两者相等。这证明两个口径是分开存的，没有混淆。

#### 发现 2：每10份分红必须除以 10，否则差 10 倍

接口返回的是字符串「每10份派现金0.2100元」。
**如果直接取第一个数字，会把「每10份」的 10 当成金额，导致每份分红恒为 1.0 元。**
这个 bug 在本阶段开发过程中真实出现过，已修正并用回归测试锁住：

```python
def test_cash_per_share_never_returns_ten():
    for raw in ("每10份派现金0.2100元", ...):
        assert _parse_cash_per_10(raw) != pytest.approx(1.0)
```

正确解析：`每10份派现金0.2100元` → 每份 0.021 元。

#### 发现 3：净值跳变必须能归因到「拆分」或「分红」，否则是异常

| 代码 | 跳变次数 | 由拆分解释 | 由分红解释 | 未解释 |
| --- | ---: | ---: | ---: | ---: |
| `161725` | 3 | 3 | 0 | **0** |
| `161005` | 2 | 0 | 2 | **0** |

**为什么这条重要**：`161725` 的单位净值从 1.0 跌到 0.5791，看数字像是亏了 42%，
但它累计净值是 2.2952 —— 说明中间有 9 次份额折算。如果只看单位净值就下结论，
会把「份额折算」误判成「亏损」。

**本阶段样本的全部跳变（5 次）都能归因，未解释 = 0。**

#### 发现 4：分红接口会返回不完整的列表

实测同一代码两次调用，`000016` 一次返回 9 条分红，一次返回 5 条。

#### 发现 5：货币基金是完全不同的数据结构

货币基金**没有单位净值**，用「每万份收益 + 7 日年化收益率」：

```
fund_money_fund_info_em('000198')
→ 净值日期 / 每万份收益 / 7日年化收益率 / 申购状态 / 赎回状态
→ 4,919 行，2013-05-30 ~ 2026-11-18
```

而且雪球基本信息接口对货币基金直接报 `KeyError: 'data'`，必须走 `fund_name_em` + 
`fund_scale_open_sina` 兜底。**架构里货币基金必须单独一张表/单独一套指标**，
不能和净值型基金混在一个 `fund_nav_daily` 里。

### 2.5 异常归零的过程说明

首轮审计报告了 2 只基金有异常，都是**验证逻辑自身的 bug**，不是数据问题：

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| 跳变日期显示为 `'570'` `'1000'` | `pct_change()` 的 index 是 RangeIndex，被当日期用 | 先 `set_index('净值日期')` 再算 |
| 分红日跳变被误判为异常 | 归因只查拆分记录，没查分红记录 | 归因同时匹配拆分日与除息日 |

修正后 **未解释异常 = 0**。这个过程本身说明：
**审计脚本必须区分「数据有问题」和「检查逻辑有问题」，不能看到报警就写进报告。**

## 3. 历史清盘基金数据可获得性（本阶段重点）

### 3.1 结论

> ## `survivorship_bias_unresolved`

**所有 AKShare 基金接口都只覆盖「当前清单」，没有任何接口返回已清盘、
已合并或已终止运作的基金名录。**

### 3.2 证据链

| # | 检查项 | 结果 |
| ---: | --- | --- |
| 1 | `fund_name_em` 是否含清盘基金 | ❌ 28,380 条全部是当前清单 |
| 2 | `fund_purchase_em` 是否有「已终止/清盘」状态 | ❌ 否，取值只有 7 种，无终止类 |
| 3 | 基金名称含「清盘/终止/清算」的 | ❌ 仅 2 条，且都是名称巧合（如「上海清算所」指数） |
| 4 | 是否有专门的清盘基金接口 | ❌ 无 |
| 5 | `fund_scale_close_sina` 是不是清盘基金 | ❌ **不是**，是「封闭式基金」，极易误读 |

### 3.3 特别警告：`fund_scale_close_sina` 是陷阱

这个接口名字里有 `close`，209 行，看起来像「已清盘基金」。

**实际是「封闭式基金」**——仍在运作、只是封闭期内不能申赎的基金。

如果把它当成清盘基金名录，会得出**完全错误**的结论：以为拿到了历史清盘数据，
实际上拿到的是一批现存的封闭式基金。这个坑必须写进架构文档。

### 3.4 为什么这很重要

如果只拿当前存续的基金去回测 2021 年以前的历史，会产生系统性偏差：

| 偏差来源 | 后果 |
| --- | --- |
| 清盘的基金被剔除 | 回测里看不到「买了之后清盘亏光」的路径 |
| 合并的基金被剔除 | 看不到合并带来的份额变更与损失 |
| 迷你基金被剔除 | 存活下来的都是规模大的，天然优质 |

**结论：任何基于当前清单的场外基金历史回测，都必须附带
`survivorship_bias_unresolved` 的限制声明，不得声称「无幸存者偏差」。**

### 3.5 可行的补充方案

1. 短期：明确标注 survivorship_bias_unresolved，所有历史回测结论必须附带该限制。
2. 中期：从基金业协会 / 证监会公告 / 天天基金清盘公告页自行构建 fund_lifecycle_events 表，按公告逐条补录。
3. 长期：建立「历史基金全量快照」机制，每期抓取全量清单留档，用快照差异反推清盘时点。

### 4.3 关键缺口

#### 缺口 1：赎回费阶梯（最严重）

场外基金赎回费按持有期限分档，典型结构：

| 持有期限 | 赎回费率 |
| --- | ---: |
| < 7 天 | 1.50% |
| 7 天 ~ 1 年 | 0.50% |
| 1 ~ 2 年 | 0.25% |
| > 2 年 | 0 |

**这套阶梯决定了短期交易策略是否可行**——如果策略平均持有 30 天，
每次赎回要付 0.5%，一年换手 12 次就是 6% 的成本。

**但 AKShare 完全没有这个字段。** 只有「申购手续费」一个数。

#### 缺口 2：A/C 份额的真实费用差异

| 项 | A 类 | C 类 |
| --- | --- | --- |
| 申购费 | 收（常 1.5%，平台打折） | 免 |
| 销售服务费 | 无 | 按年收（常 0.4%~0.8%） |
| 赎回费 | 按期限阶梯 | 通常 7 天内 1.5%，之后 0 |

接口只能看到 A/C 的申购手续费不同（C 常为 0），**销售服务费完全没有字段**。
这意味着无法做 A/C 的真实成本对比。

#### 缺口 3：基金转换

**完全没有接口。** 同公司基金间的转换费率、限制、是否支持，全部无法获取。

#### 缺口 4：支付宝可购买状态

> **标记为 `unknown`。**

支付宝代销名单是**动态信息**，AKShare 没有任何字段反映它。

即使某只基金在天天基金「开放申购」，也**不能**推断它在支付宝能买到——
两个平台代销名单不同、折扣不同、限额不同。

**在没有可靠证据前，不得声称任何基金一定可以在支付宝购买。**

### 6.0 净值日期连续性专项审计（3B-3.1 补强）

#### 6.0.1 检查项与判定口径

| # | 检查项 | 是否能独立判定 |
| ---: | --- | --- |
| 1 | 净值日期重复 | ✅ 不依赖日历 |

| 7 | 首末日期与有效行数 | ✅ |

**关于「可靠日历」的诚实说明**：

项目数据库里的 `trade_calendar`（8,797 天，1990-12-19 ~ 2026-12-31）

- 新基金成立初期常按周公布，之后才转每日；

- 暂停估值、巨额赎回等特殊情形。

因此本节的结论一律标注 `verification_level = proxy`（代理验证），
**不构成「某日在任何情况下都应有净值」的绝对证明**。

## 7. 数据库模型设计（只设计，不迁移）

> **本阶段只输出设计，**未执行任何数据库迁移****

### 7.1 十张表

| # | 表 | 用途 |
| ---: | --- | --- |
| 1 | `fund_master` | 基金本体（一只基金一行，A/C 份额共用） |
| 2 | `fund_share_classes` | 份额类别（A/C/E/I 等），一个基金本体多行 |
| 3 | `fund_nav_daily` | 每日净值（单位净值 + 累计净值，分开存） |
| 4 | `fund_dividends` | 分红记录 |
| 5 | `fund_manager_history` | 基金经理任职历史 |
| 6 | `fund_aum_history` | 规模历史 |
| 7 | `fund_fee_rules` | 费率规则（申购/赎回/销售服务） |
| 8 | `fund_subscription_status` | 申购/赎回状态快照 |
| 9 | `fund_lifecycle_events` | 生命周期事件（成立/清盘/合并/份额变更） |
| 10 | `fund_data_quality` | 数据质量状态 |

### 7.2 关键设计点

- 基金本体与份额分两级，A/C 不重复计数
- 单位净值与累计净值分列，禁止混用
- 所有表保留 source / ingested_at / data_version
- 生命周期事件单独建表，清盘与合并有落点
- 申购状态按日快照，才有历史可回溯
- 费率按阶梯存，赎回费必须有 holding_days 区间

### 7.3 核心表结构

#### `fund_master`

**用途**：基金本体（一只基金一行，A/C 份额共用）

**主键**：`fund_id (surrogate) + fund_code_primary`

**字段**：`fund_id`、`fund_code_primary`、`fund_name`、`fund_full_name`、`fund_company`、`custodian`、`fund_type_l1`、`fund_type_l2`、`invest_scope`、`benchmark`、`established_date`、`terminated_date`、`lifecycle_status`、`is_index_fund`、`tracking_index`、`source`、`source_updated_at`、`data_version`

**说明**：terminated_date 是清盘日的落点；当前数据源拿不到，必须先留字段

#### `fund_share_classes`

**用途**：份额类别（A/C/E/I 等），一个基金本体多行

**主键**：`share_class_id + (fund_id, share_class_code) UNIQUE`

**字段**：`share_class_id`、`fund_id`、`share_class_code`、`share_class_name`、`share_class_type`、`currency`、`is_primary`、`management_fee`、`custody_fee`、`sales_service_fee`、`min_purchase`、`min_holding`、`listed_date`、`terminated_date`、`source`、`source_updated_at`

**说明**：**A/C 在这里区分，不在 fund_master 里**，避免基金数量重复计数

#### `fund_nav_daily`

**用途**：每日净值（单位净值 + 累计净值，分开存）

**主键**：`(share_class_id, nav_date) PK`

**字段**：`share_class_id`、`nav_date`、`unit_nav`、`acc_nav`、`daily_return`、`nav_status`、`source`、`ingested_at`

**说明**：**单位净值与累计净值必须是两列**，混用是本项目已知的历史错误来源

#### `fund_dividends`

**用途**：分红记录

**主键**：`(share_class_id, ex_date) PK`

**字段**：`share_class_id`、`record_date`、`ex_date`、`pay_date`、`cash_per_share`、`dividend_type`、`reinvest_nav`、`source`、`ingested_at`

**说明**：每10份分红必须归一化为每份，否则与净值口径差 10 倍

#### `fund_manager_history`

**用途**：基金经理任职历史

**主键**：`(fund_id, manager_name, start_date)`

**字段**：`fund_id`、`manager_name`、`company`、`start_date`、`end_date`、`tenure_days`、`source`、`ingested_at`

**说明**：**当前接口只给现任经理，没有起止日期**，start_date 需人工/公告补录

#### `fund_aum_history`

**用途**：规模历史

**主键**：`(share_class_id 或 fund_id, report_date)`

**字段**：`fund_id`、`share_class_id`、`report_date`、`aum_total`、`shares_total`、`aum_unit`、`source`、`ingested_at`

**说明**：接口只给「最新规模」，历史规模要按季报补

#### `fund_fee_rules`

**用途**：费率规则（申购/赎回/销售服务）

**主键**：`(share_class_id, fee_type, tier_order)`

**字段**：`share_class_id`、`fee_type`、`tier_order`、`lower_bound`、`upper_bound`、`rate`、`holding_days_min`、`holding_days_max`、`effective_from`、`effective_to`、`source`、`evidence_level`

**说明**：**赎回费阶梯必须有**，当前数据源完全没有

#### `fund_subscription_status`

**用途**：申购/赎回状态快照

**主键**：`(share_class_id, as_of_date)`

**字段**：`share_class_id`、`as_of_date`、`purchase_status`、`redeem_status`、`daily_limit`、`min_purchase`、`next_open_date`、`source`、`ingested_at`

**说明**：必须**按日留快照**才有历史，单次抓取只是当日状态

#### `fund_lifecycle_events`

**用途**：生命周期事件（成立/清盘/合并/份额变更）

**主键**：`event_id + (fund_id, event_date, event_type)`

**字段**：`event_id`、`fund_id`、`event_type`、`event_date`、`announcement_date`、`announcement_url`、`detail`、`successor_fund_id`、`evidence_level`、`source`、`ingested_at`

**说明**：**清盘/合并就落这张表**；当前无数据源，是架构的第一优先补齐项

#### `fund_data_quality`

**用途**：数据质量状态

**主键**：`(table_name, record_key, check_name)`

**字段**：`table_name`、`record_key`、`check_name`、`status`、`detail`、`checked_at`、`severity`

**说明**：沿用项目已有 data_quality 思路，独立于 ETF 侧

### 7.4 为什么必须拆两级

如果只有一张 `fund` 表，用基金代码做主键，会得到：

| 做法 | 结果 |
| --- | --- |
| 单表 + 代码主键 | 28,380 个「基金」，其中约 21,000 个是份额 |
| 两级 | 约 15,000 个基金本体 + 28,380 个份额 |

**多算的 1 万多只是纯虚增**，会让「市场上有多少只基金」「平均规模多少」
这类统计全部失真。

## 8. 现有模块复用分析

### 8.1 可复用（6 项）

| 模块 | 判断 | 说明 |
| --- | --- | --- |
| 指标计算（MA/RSI/MACD/波动率） | ✅ 可复用 | 算法本身与标的是场内还是场外无关；需要新的数据适配层喂入 |
| 风险指标（Sharpe/Sortino/Calmar/最大回撤） | ✅ 可复用 | 基于净值序列，场外基金同样适用 |
| 组合分析（权重、再平衡、归因） | ✅ 可复用 | 逻辑层与执行层解耦后可复用 |
| 报告生成 | ✅ 可复用 | 仅需替换数据来源与字段名 |
| 数据质量检查框架 | ✅ 可复用 | 检查规则需新增场外基金特有项（如净值停更、份额拆分） |
| 研究框架（脚本 + JSON + 报告 + 测试） | ✅ 可复用 | 3B-1/3B-2/3B-3 已形成稳定范式 |

### 8.2 需要单独建设（5 项）

| 模块 | 原因 |
| --- | --- |
| 场外基金净值数据层 | 标的、频率、字段全部不同 |
| 申购赎回执行模型 | T+1 确认、15:00 截止、按净值成交，与场内撮合完全不同 |
| 基金费率模型 | 申购费/赎回费阶梯/销售服务费，场内没有 |
| 基金经理与份额管理 | 场内 ETF 没有这个概念 |
| 场外基金回测适配层 | 把现有引擎的撮合换成绩效确认模型 |

### 8.3 硬边界

> **不把场内 ETF 回测引擎改造成场外基金引擎。** 两者交易模型差异是结构性的（撮合 vs 确认、日内 vs T+1、价格 vs 净值），改造成本高于重建。

**具体差异**：

| 维度 | 场内 ETF | 场外基金 |
| --- | --- | --- |
| 价格 | 实时撮合价 | 每日一个净值 |
| 成交 | 即时（秒级） | T+1 确认 |
| 到账 | T+0（卖出即刻可用） | T+3 ~ T+7 |
| 费用 | 佣金 + 印花税 | 申购费 + 赎回费阶梯 + 销售服务费 |
| 最小单位 | 100 份 | 1 元起（部分 0.01 元） |
| 折溢价 | 有 | 无 |
| 停牌/限购 | 交易所停牌 | 暂停申购/限大额 |

**这些差异不是参数不同，是交易模型不同**，所以不能改造现有引擎。

## 9. 不能解决的问题

| # | 问题 | 严重性 | 能否缓解 |
| ---: | --- | --- | --- |
| 1 | **清盘基金名录完全缺失** | 🔴 高 | 需自建，从公告抓取 |

| 3 | **销售服务费无字段** | 🟡 中 | 同上 |
| 4 | **基金转换规则无接口** | 🟡 中 | 短期放弃该功能 |
| 5 | **支付宝可购买状态 unknown** | 🟡 中 | 无法自动获取 |
| 6 | **申购状态无历史** | 🟡 中 | 需按日快照积累 |
| 7 | **规模历史只有当前值** | 🟢 低 | 按季报补 |
| 8 | **经理任职起止缺失** | 🟢 低 | 从公告补 |
| 9 | **货币基金基本信息需兜底** | 🟢 低 | 已实现兜底 |
| 10 | **分红接口偶发不完整** | 🟢 低 | 已实现两次校验 |

### 9.1 最严重的两个

**问题 1 和 2 是真正的阻塞项**：

- 没有清盘数据 → **任何历史回测都带幸存者偏差**，结论不可信
- 没有赎回费阶梯 → **无法计算真实交易成本**，高频策略的结论会严重失真

这两个不解决，就不能做「场外基金策略回测」，只能做「净值分析」。

### 10.1 优先级排序

| P2 | 申购状态按日留快照 | 为将来的可交易性建模积累数据 |
| P2 | 规模历史、经理任职历史 | 从季报/公告补 |
| P3 | 支付宝可购买状态 | 需外部证据，短期标 unknown |

### 10.2 建议的分阶段路径

**第一步（先做净值层，可立即开始）**

- 建 `fund_master` / `fund_share_classes` / `fund_nav_daily` / `fund_dividends`
- 灌入全量基金的历史净值（按需，不必一次全灌）
- 做净值层面的分析：收益、波动、回撤、相关性
- **不做交易模拟**，因为这些只能算「持有收益」，不能算「策略收益」

**第二步（补清盘与费用，才能做回测）**

- 从基金业协会、证监会公告、天天基金清盘公告页抓 `fund_lifecycle_events`
- 从基金合同/招募说明书录入 `fund_fee_rules`
- 建 `fund_subscription_status` 按日快照
- 此时才具备做场外基金回测的数据前提

**第三步（建独立的场外基金回测适配层）**

- **新建**，不是改造现有 ETF 引擎
- 交易模型：T 日 15:00 前提交 → T 日净值成交 → T+1 确认份额
- 费用模型：申购费 + 赎回费阶梯 + 销售服务费（按持有天数）
- 可交易性：暂停申购时不能买入，暂停赎回时不能卖出

### 10.3 不建议做的事

| 不建议 | 原因 |
| --- | --- |
| 把现有 ETF 回测引擎改造成场外基金引擎 | 交易模型差异是结构性的，改造成本高于重建 |
| 用当前存续基金回测 2021 年前历史并声称有效 | 幸存者偏差未解决，结论不可信 |
| 假设所有基金都是 T+1 确认 | 实际差异很大，QDII 是 T+2 |
| 用「手续费」字段当作合同申购费率 | 是列表页展示值，不等于合同费率 |
| 假设基金在支付宝可购买 | 无证据，必须标 unknown |

## 13. 结论

### 13.1 一句话

> **场外基金的净值数据完全可用，但「能不能买、卖的时候扣多少、会不会清盘」
> 这三件事现在都没有可靠数据源——所以可以做净值分析，还不能做真实回测。**

### 13.2 可以立刻开始的事

1. 建 `fund_nav_daily` 层，灌历史净值（数据源可靠、字段完整）
2. 做净值层面的分析（收益、波动、回撤、相关性、A/C 差异）
3. 记录 `survivorship_bias_unresolved` 并在所有结论中声明

### 13.3 必须先解决才能做回测的事

1. **清盘基金名录**（否则历史回测全部带幸存者偏差）
2. **赎回费阶梯**（否则交易成本算不出来）
3. **申购状态历史**（否则不知道当时能不能买）

### 13.4 立场声明

本阶段**没有**声称：

- 任何基金有投资价值
- 任何策略可以赚钱
- 数据已完整
- 幸存者偏差已消除

本阶段**只**回答了：哪些数据能拿到、哪些拿不到、拿不到的怎么办。
