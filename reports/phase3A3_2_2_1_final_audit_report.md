## 4. 登记日缺失问题如何处理

### 4.1 旧行为（错误）

```python
if action.action_id in self._dividend_locked_shares:
    holding = self._dividend_locked_shares[action.action_id]
else:
    holding = portfolio.quantity(action.code)   # ← 退回除息日持仓
```

**后果**：回测开始后才买入的份额，如果登记日在回测起点之前，
会因为「除息日持有」而凭空获得分红资格。

### 4.2 新行为（fail closed）

```python
if action.action_id not in self._dividend_locked_shares:
    # 记录阻断原因，直接 continue，不计应收
```

阻断原因精确区分：

| 情形 | reason_code | 说明 |
| --- | --- | --- |
| 登记日早于回测起点 | `missing_record_date_holding` | 无法取得合法持仓证据 |
| 登记日在区间内但无交易日数据 | `missing_record_date_holding` | 同上 |

`blocked_actions` 记录事件 ID、代码、日期、原因，不进应收。

### 4.3 本库实际影响

| 项 | 数量 |
| --- | ---: |
| 区间内分红事件 | 81 条中 57 条为分红 |
| 登记日全部在区间内 | **57/57** |
| 因登记日缺失被阻断 | **0** |

原因：所有分红事件的 `record_date` 都在 2021-01-04 之后，
且都落在交易日。

## 5. cash_compensation 是否具备安全执行条件

### 5.1 结论：**不具备，且本库不需要**

| 项 | 状态 |
| --- | --- |

| 公告规定现金补偿的条数 | **0** |
| 强制要求补偿价格依据 | **已实现** |
| 缺依据时是否阻断 | **是，抛 `CorporateActionError`** |

### 5.2 新增字段

| 字段 | 作用 |
| --- | --- |
| `compensation_price` | 官方补偿价格（元/份） |
| `compensation_price_source` | 价格依据（公告条款原文或计算公式） |

两条约束：

1. `__post_init__`：声明 `cash_compensation` 但缺 `compensation_price_source` → 构造即抛错
2. `compute_impact`：缺价格或依据 → 抛 `CorporateActionError`

同时两者已纳入事件指纹，补偿价格改动会改变 `input_hash`。

### 5.3 关键修复

旧代码 `compensation_price=price if ... else None` ——
`price` 是**事件日收盘价**，被当作官方补偿价格。

新代码：

```python
compensation_price=(action.compensation_price
                    if policy == FRACTION_CASH_COMPENSATION else None)
```

只用 `action.compensation_price`（官方值），不碰收盘价。

测试 `test_cash_compensation_with_official_price_uses_that_price`
传入收盘价 99 元、官方价 50 元，断言用的是 **50 元**。

### 6.2 报告说的 171 不对在哪

上一份报告算的是：

```
166（证据等级）+ 5（fractional_policy）= 171
```

**漏掉了 11:24 那 5 行。**

### 6.3 多出的 5 行来自什么

`round_up` 口径被写入**两次**（11:24 和 11:29），每次 5 条：

```
11:24  第一次写入 5 条 round_up
11:29  第二次写入 5 条 round_up（内容相同）
```

**原因是 `save_action` 的幂等缺陷**：

```python
if old_fp == fingerprint:
    return action_id       # ← 指纹相同就早退
```

第一次写入时 `fractional_policy` 列没有真正落库（UPDATE 语句漏了该列），
但 `event_fingerprint` 已经更新。第二次执行脚本时：
- 新指纹 == 库内指纹 → 早退 → 不写

但脚本实际报告「更新 5 条」并产生版本。真实链路是：
第一次写入了指纹但没写 policy → 第二次检测到指纹相同（因为对象携带新指纹）
→ 但库内 `fractional_policy` 仍是旧值 → 触发「关键列不一致」→ 重新写入。

**这个缺陷已在 3A.3.2.2 修复**（早退条件加上关键列比对），
所以第二次写入的 5 个版本是**缺陷行为的历史痕迹**，
按纪律**不删除**，保留完整审计记录。
